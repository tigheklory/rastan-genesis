The 1994 AFTER BURNER COMPLETE 32X cartridge (2 MB) measured byte-for-byte against the 27 original After Burner II arcade ROMs. Same question as Space Harrier: how much of the arcade machine is actually inside the cart?

01

The same three layers

After Burner II runs on Sega's X Board — a bigger, later Super Scaler design than Space Harrier, with two 68000s both substantially larger. Rutubo split it the same way.

Thrown away

Both engines

The main 68000 code (reset, main loop, X-Board hardware setup at $140000/$e8010) and the sub 68000 code (the $55555555 master/slave handshake, the per-frame loop) are absent — 7.6% in the sub's code zone, the entry code not found at all. Standard "MARS" boot.

Copied verbatim

Data & math tables

The main-CPU mission/object data (up to 78% of some banks) and — the headline — the sub-CPU's sprite-projection & scaling tables at 94% are embedded intact. The arcade sound Z80 is ~49% reused.

Reinvented

The Super Scaler

All 16 sprite ROMs, the tiles, the road and the PCM samples are gone / re-encoded. The SH-2 pair performs the scaling the X-Board hardware did — but it does it using the arcade's own copied scaling tables.

Where the arcade lives in the cart

The full 2 MB image. The arcade-derived content sits in one data cluster near the front and a block of reused sound near the back; the rest is Rutubo's native 32X payload.

Native 32X code / re-encoded assets Arcade Z80 sound (~49%) Arcade main-CPU data (partial) Arcade sub-CPU 3D tables (94%)

Arcade data clusters across 0x01E000–0x052000 (main mission data flowing straight into the sub-CPU math tables), with reused sound near 0x17C000. The intervening ~1.4 MB and the tail are the native 32X engine, SH-2 renderer and re-encoded graphics.

04

What Rutubo did here

After Burner II is a heavier machine than Space Harrier — the X Board carries two full-size 68000 programs (256 KB each) because the sub-CPU is doing continuous 3D work: projecting and scaling the jet, enemies, missiles and the banking horizon every frame. That makes the triage more interesting, but the principle is identical to the Space Harrier cart:

  1. The executable cores of both 68000s were rewritten. Neither the main engine code nor the sub-CPU's projection code is in the cart (the sub code zone scores 7.6%, and the exact entry-code bytes are not present). As with Space Harrier, the ROM boots through the stock "MARS" 32X stub into fresh code.
  2. The sub-CPU's math tables were too valuable to recompute. The X-Board sub-CPU leans on large baked tables — sprite zoom/projection, scaling and object data. Reproducing those exactly is tedious and error-prone, so Rutubo copied them in whole: 94% of the sub-CPU data region lands in the cart at 0x429D0. The SH-2 software scaler then renders using the arcade's own numbers — which is as literal as "the 32X takes over the Super Scaler" ever gets.
  3. Main-CPU mission data came along too. The stage/enemy/attack-pattern tables in the upper main program (up to ~78% of one bank) were reused, matching how Space Harrier's stage data was lifted.
  4. Sound reused where the chip matches. The arcade sound CPU is a Z80 and so is the Genesis's, so ~49% of the sound ROM — driver plus sequence data — carries over, parked near 0x17C000.
  5. Everything format-bound was re-encoded. All sixteen sprite mask ROMs (a full 2 MB on the arcade), the tiles, the road graphics and the half-megabyte of PCM are absent, rebuilt for the SH-2 framebuffer, the Genesis VDP and the Genesis sound path.

The one real difference from Space Harrier

Space Harrier's ground is a flat checkerboard, so its sub-CPU had little worth keeping and was dropped almost entirely. After Burner's sub-CPU is a genuine 3D projector, so its data — not its code — became the single largest arcade lift in the cart. Same strategy, applied to a harder problem: keep the expensive numbers, rewrite the machine that uses them.

Method & caveats

The 32X image (After Burner 32X (A) [!].32x, 2,097,152 bytes, header name AFTER BURNER COMPLETE) was de-interleaved into even/odd streams and each arcade ROM searched against the raw image and each half using 32-byte high-entropy windows; blocks were confirmed by extending exact contiguous runs and by 68000 disassembly. "Code zone" vs "data zone" of each program was separated by disassembly and by per-region coverage: the sub-CPU's code region (around entry 0x402) is 7.6% present while its table region (0x20000–0x3C000) is 94% present. Whether the Genesis 68000 executes any lifted bytes or only reads them as data was not instrumented; the verbatim, un-relocated copies are consistent with data/table reuse rather than re-hosted code.
