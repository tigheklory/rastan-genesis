ROM teardown · Sega 32X vs. arcade Super Scaler

Is Space Harrier 32X
running the arcade ROMs?

A byte-level comparison of the 1994 Sega 32X cartridge (2 MB) against the 51 original arcade EPROMs, testing the long-standing rumor that Rutubo Games re-hosted the arcade 68000 program on the Genesis while the SH-2s stood in for the arcade's Super Scaler sprite hardware.

Verdict: the rumor is half true. The arcade engine was rewritten, but entire arcade data banks and the sound program were lifted verbatim into the cart — and the Super Scaler really was replaced in software.

01

Three things at once

A port is rarely all-or-nothing. Space Harrier 32X splits cleanly into three layers — one thrown away, one copied, one reinvented.

Thrown away

The engine

The arcade main-CPU boot bank (vectors, main loop, Super Scaler driver) and the second 68000's program are absent (0–3%). The cart boots through the stock Sega "MARS" 32X stub into brand-new code.

Copied verbatim

The data & sound

The upper three banks of the arcade main program — the stage, enemy and pattern data tables — and the arcade Z80 sound program are embedded byte-for-byte. One 64 KB bank matches 100%.

Reinvented

The rendering

Every hardware-format asset — zoomable sprites, tiles, the road, PCM samples — is gone and re-encoded. The SH-2 pair redraws the scaled sprites the Super Scaler used to do in silicon.

04

What Rutubo actually did

The arcade Space Harrier board is a Super Scaler machine: two 68000s, a Z80 + SegaPCM for sound, dedicated hardware that scales hundreds of sprite cels in real time, and a separate road/ground generator. None of that silicon exists on a Sega 32X. What the 32X does have is a Genesis-side 68000 plus two SH-2 RISC CPUs and a framebuffer. Rutubo's job was to reproduce an arcade hardware game on hardware with a completely different shape — and the byte evidence shows exactly how they triaged it:

  1. Keep the arcade's "what", throw away its "how". A game like Space Harrier is mostly data — tables that say which enemy appears, where, when, moving on which pattern, in which of the 18 stages. That data lived in the upper banks of the arcade main-CPU ROM, and it is hardware-independent. Rutubo copied those banks straight into the cart (bank 2 is a 100% byte-for-byte 64 KB match at 0x5A0AE), then wrote a fresh engine to read them.
  2. Rewrite the engine. The arcade's executable core — reset vectors, the trap #$a task dispatcher, the main loop, and the code that programmed the Super Scaler and road chips — is not in the cart at all. It was re-authored for the 32X, which is why the ROM boots through the standard Sega "MARS" 32X security/init stub like any other 32X title, not into arcade code.
  3. Move the Super Scaler into software on the SH-2s. The arcade's sprite-scaling hardware has no 32X equivalent, so its job — taking a sprite cel and drawing it at an arbitrary zoom into the scene — was reimplemented as SH-2 code rendering into the 32X framebuffer. This is the grain of truth the rumor latched onto: the 32X genuinely performs the Super Scaler's function, just not by running the arcade's sprite code.
  4. Re-encode every format-bound asset. The zoomable sprite cels (32 ROMs), background tiles, road patterns, the zoom lookup table and the PCM samples are all stored in arcade-specific bit layouts. Every one of them is absent from the cart — re-encoded for the SH-2 renderer, the Genesis VDP and the Genesis sound path.
  5. Reuse the sound program where the hardware lines up. The arcade sound CPU is a Z80 — and the Genesis has a Z80 too. So the arcade Z80 sound driver and its sequence data were carried over substantially (~60% of the two sound ROMs appear in the cart near 0x9000), the one place an arcade program could survive largely intact.

So the honest one-liner: Space Harrier 32X is a from-scratch 32X engine wrapped around the arcade game's original data and sound. Not an arcade-68000 "ReROM," but much closer to one than a blind reimplementation — the actual content of the game is the arcade's, lifted intact; only the machinery that renders and runs it is new.

Could you turn it into Enduro Racer?

Enduro Racer runs on the same Sega Super Scaler board family (dual 68000 + scaled sprites + road + Z80/SegaPCM). So the arcade source material is structurally familiar — but Rutubo's 32X code is not a generic "Super Scaler console." Here's the honest accounting.

  • The whole road model: hills, crests, curves, jumps

Near-total rewrite

Same arcade hardware family saves you asset conversion and gives a reference build to match — but Rutubo's engine is bespoke to Space Harrier's rail-shooter camera and flat checkerboard ground. Enduro Racer's defining feature is a winding, hilly road with jumps: a fundamentally harder and different renderer. You'd keep the low-level 32X plumbing and the sound approach, and rewrite essentially everything that makes it a game.

Bottom line: it is not a ROM-swap. Dropping Enduro Racer's arcade data banks into the Space Harrier 32X would produce nothing runnable, because the engine that interprets those banks — and especially the road renderer — is specific to Space Harrier. Converting it is roughly the same project Rutubo did the first time: a ground-up 32X port that happens to start from a very good head start on the low-level 32X and sound layers.

Method & caveats

The 32X image (Space Harrier 32X (JU) [!].32x, 2,097,152 bytes) was de-interleaved into even/odd byte streams and every arcade EPROM was searched against the raw image and each half using 32-byte high-entropy content windows; embedded blocks were confirmed by extending exact contiguous runs and by 68000 disassembly of the reconstructed pairs. Coverage percentages ignore trivial all-zero / all-$FF windows. "Verbatim" means a byte-exact contiguous run (bank 2 extends to a full 65,536-byte match). Whether the Genesis 68000 executes any copied bank or merely reads it as data was not instrumented; the verbatim, un-relocated copy is consistent with data-table reuse rather than re-hosted code, since executable arcade code would carry arcade-hardware addresses needing patches that would break the exact match. Arcade ROM roles are from MAME's segahang.cpp sharrier set. Original ROM files were treated as read-only; all analysis ran on copies.
